# 이체 한도 QA 자동화

이체 한도 기능을 대상으로, **정합성 불변식**을 정의하고 자동으로 감시하는 테스트를 구성했습니다.
가상의 시뮬레이터를 대상으로 하며 실제 서비스와는 무관합니다.

## 실행 링크

GitHub Pages에 배포되어 있습니다. 별도 서버/DB 설정 없이 링크만으로 열립니다.

**https://mingyu-kim33.github.io/transfer-limit-qa/**

저장소 루트의 `index.html`과 `vendor/`는 Pages 배포용 사본이며 `app/`과 동일한 파일입니다.
테스트는 `app/`을 대상으로 실행됩니다.

로컬에서 열 때는 `app/index.html`을 바로 열어도 되지만, 일부 브라우저의 WebAssembly 보안 정책상
정적 서버로 여는 걸 권장합니다: `cd app && python -m http.server 8000`

## 테스트 실행

```bash
pip install -r requirements.txt
playwright install chromium
pytest
```

각 테스트는 새 브라우저 컨텍스트를 받으므로 sql.js 인스턴스와 원장이 테스트마다 격리됩니다.

## 서버 없이, 링크 하나로 동작합니다

이 앱은 별도 백엔드가 없습니다. **sql.js**(WebAssembly로 컴파일된 진짜 SQLite)를
브라우저 안에서 직접 구동해, 정적 파일만으로 실제 SQL이 실행되는 원장을 갖췄습니다.
그래서 GitHub Pages 같은 정적 호스팅에 그대로 올려 링크 하나로 접속해 조작해볼 수 있습니다.

## 화면과 DB를 분리했습니다

소진액은 브라우저가 들고 있는 JS 상태값이고, 원장(`transfer_ledger`)은 이체마다
sql.js DB에 INSERT되는 별도 저장소입니다. 테스트는 Playwright의 `page.evaluate`로
브라우저 안의 sql.js에 실제 SQL을 실행해, 화면 값과 각각 읽어 대조합니다.

```sql
SELECT COALESCE(SUM(amount), 0) FROM transfer_ledger
WHERE status = 완료 AND biz_date = ?
```

같은 화면 안에서 자기 자신을 대조하면 렌더 로직이 틀렸을 때 양쪽이 같이
틀립니다. DB를 앱 바깥에 두고 SQL로 직접 조회해야 독립적인 대조가 됩니다.
DEF-02(전날 건 취소가 오늘 소진액을 차감하던 결함)를 잡아낸 것도 이 대조입니다.

## 왜 케이스가 아니라 불변식인가

케이스 기반 테스트는 사람이 상상한 조합까지만 검증합니다.
돈이 오가는 기능에서 실제로 사고가 나는 지점은 대체로 상상하지 못한 조합입니다.

그래서 이 프로젝트는 두 층으로 나눴습니다.

- **케이스 층**: 한도 경계, 누적, 취소, 일자 변경처럼 명시적으로 정의된 규칙을 확인
- **불변식 층**: 어떤 경로로 조작되든 항상 참이어야 하는 규칙을 정의하고, 모든 동작 뒤에 검사

불변식은 케이스 테스트 안에서도 매번 함께 검사되고,
무작위 시퀀스 테스트에서 수백 회 반복 검증됩니다.

## 정의한 불변식

| ID | 규칙 | 깨졌을 때의 의미 |
|---|---|---|
| TOSS-01 | 화면 소진액 = 원장의 당일 합계 | 화면의 잔여 한도를 신뢰할 수 없음 |
| TOSS-02 | 소진액 ≤ 1일 한도 | 한도가 기능하지 않음 |
| TOSS-03 | 잔여 한도 ≥ 0 | 이후 계산이 전부 오염됨 |
| TOSS-04 | 잔여 한도 = 1일 한도 − 소진액 | 표시되는 숫자끼리 어긋남 |
| TOSS-05 | 완료 건은 이체 시점의 1회 한도 이하 | 단건 상한이 우회됨 |
| TOSS-06 | 화면이 표시하는 원장 합계 = 레코드 직접 집계값 | 집계 로직 자체가 틀림 |

## 구조

```
transfer_limit_qa/
├── app/
│   ├── index.html                  [테스트 대상 시뮬레이터: 서버 없이 완전히 독립 실행]
│   └── vendor/                     [sql.js: 브라우저 내장 SQLite(WebAssembly), 로컬 번들]
├── pages/
│   └── transfer_page.py            [Page Object Model: page.evaluate로 sql.js에 SQL 직접 실행]
├── tests/
│   ├── conftest.py                 [정적 서버 / 브라우저 fixture]
│   ├── invariants.py               [불변식 정의: 이 프로젝트의 핵심]
│   ├── test_limit_rules.py         [경계값 / 누적 / 취소 / 롤오버]
│   ├── test_random_sequence.py     [무작위 시퀀스 + 불변식 검사]
│   └── test_regression_found_defects.py  [발견된 결함의 회귀 테스트]
├── .github/workflows/ci.yml
├── logs/                           [발견 전 / 후 실행 로그]
├── index.html                      [Pages 배포용 사본: app/index.html과 동일]
└── vendor/                         [Pages 배포용 사본: app/vendor와 동일]
```

## 설계 원칙

- 모든 요소에 `data-testid`를 부여해 스타일/DOM 구조 변경과 테스트를 분리
- 화면 접근은 Page Object 안에만 두어 마크업 변경의 영향 범위를 한 파일로 제한
- 경계값은 손으로 나열하지 않고 한도 값에서 생성: 한도가 바뀌면 테스트도 따라감
- 무작위 테스트는 seed를 고정해 재현 가능하게 두고, 위반 시 동작 순서를 그대로 출력해
  수동 재현 절차서로 쓸 수 있게 함
- 영업일은 화면에 2026-09-14 형태로 표시하되 내부 계산과 DB 적재는 기준일 오프셋 정수를 사용.
  Page Object가 화면 날짜를 오프셋으로 환산해 비교하므로 표시 형식이 바뀌어도 검증 로직은 영향 없음

## 발견한 결함

무작위 시퀀스 테스트가 불변식 위반으로 잡아낸 결함들입니다.
모두 정상 흐름 테스트로는 드러나지 않았습니다.

| ID | 내용 | 불변식 | 영향 |
|---|---|---|---|
| DEF-01 | 동시 요청 시 한도 검사가 요청 전 스냅샷 기준이라 두 건이 각각 통과 | TOSS-02, TOSS-03 | 1일 한도를 초과한 이체가 성립 |
| DEF-02 | 지난 날짜의 이체를 취소하면 오늘 소진액에서 차감 | TOSS-01 | 소진액이 음수가 되어 당일 한도를 우회 |
| DEF-03 | 이미 소진한 금액보다 낮게 한도를 하향 가능 | TOSS-03, TOSS-04 | 잔여 한도가 음수로 노출 |

발견된 결함은 모두 `test_regression_found_defects.py`에 결정적 케이스로 옮겨
회귀를 막았습니다. 무작위 테스트는 매번 같은 경로를 밟지 않기 때문입니다.

## 불변식 정의를 두 번 고친 기록

검증 과정에서 앱이 아니라 불변식 쪽이 틀린 경우도 있었습니다.

- TOSS-01은 처음에 전체 내역 합계와 소진액을 비교했습니다. 일자가 바뀌면 소진액만
  초기화되므로, 당일 완료 건만 대조하도록 범위를 좁혔습니다.
- TOSS-05는 현재 1회 한도와 과거 이체를 비교했습니다. 한도 하향은 미래 건에만
  적용되므로, 이체 시점의 한도를 함께 기록하고 그 값과 대조하도록 바꿨습니다.
  금융 기능에서 적용 시점 기록이 왜 필요한지가 여기서 드러났습니다.

불변식은 한 번에 맞게 쓰이지 않습니다. 위반이 났을 때 제품과 규칙 중
어느 쪽이 틀렸는지를 판단하는 것까지가 검증 과정이라고 봤습니다.

## UI 전면 수정 후 

레이아웃, 색상, 컴포넌트 구조를 모두 바꾸고 게이지/칩/상태 배지를 새로 추가했지만,
테스트 코드와 Page Object는 한 줄도 수정하지 않았습니다.

모든 요소를 `data-testid`로만 접근했기 때문입니다. 클래스명이나 DOM 경로에
의존했다면 개편과 동시에 전부 깨졌을 겁니다. 자동화의 유지비는 대부분
여기서 갈립니다.
